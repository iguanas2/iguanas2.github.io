Ilusion Life Countervoltar

ILC is a minimal two-player life counter designed to run on extremely limited web environments, specifically older Kindle devices using the early HTML5-era browser implementation available around 2009.


The project intentionally avoids modern JavaScript APIs, frameworks, build systems, and complex DOM manipulation. Its implementation is deliberately simple so that the page can continue working on old and restricted browser engines.

Why the code looks unusual

The code may look unnecessarily simple or outdated compared to a modern web application. This is intentional.


The target environment is an old Kindle browser, where many features commonly used today either did not exist, were poorly supported, or consumed unnecessary resources. Because of this, the project follows a "lowest common denominator" approach: use features that are old, widely implemented, and unlikely to depend on modern browser behavior.


Inline onClick handlers

Instead of using modern event listeners such as:

button.addEventListener("click", ...);

the buttons directly call the function:

<button onClick="changeScore(this,1)">+</button>

This is an older style of JavaScript interaction, but it has an important advantage for this project: it relies on very basic browser functionality.


There is no initialization code, event-registration system, module system, or framework required. The browser simply executes the function when the button is pressed.

The this argument is also useful because it passes the button that was clicked directly to changeScore().

Using this to identify the player

The JavaScript does not assign unique IDs to every player.


Instead, it determines which player owns the clicked button:


const player = button.closest('.player');

This keeps the HTML repetitive but extremely small. Both players can use exactly the same JavaScript function.


The function therefore does not need separate functions such as:

increasePlayer1(); decreasePlayer1(); increasePlayer2(); decreasePlayer2();

One function handles every score button.

closest() and compatibility considerations

The use of:

button.closest('.player')

is one of the more questionable parts of the implementation for a 2009-era browser.

Element.closest() is a much newer DOM API and was not part of the original 2009 browser environment. Modern browsers support it, but an old Kindle browser may not.

This is especially important because the project includes:

<script src="polyfill.min.js"></script>

The polyfill is intended to provide compatibility for JavaScript features that the original browser does not understand.

However, this also means the project depends on the specific contents of polyfill.min.js. Without the appropriate polyfill, closest() could cause the score buttons to fail entirely on an older browser.

For maximum compatibility, the closest() call could be replaced with older DOM traversal methods.

textContent instead of modern DOM techniques

The score is updated using:

scoreElement.textContent = parseInt(scoreElement.textContent) + amount;

This deliberately performs a very small amount of DOM manipulation.


There is no virtual DOM, state management library, reactive framework, or application state. The displayed number itself acts as the stored value.

When the user presses +:


20 → 21


and when they press -:



20 → 19


The existing text is converted to an integer with parseInt(), modified, and written back to the page.


This approach is primitive by modern standards, but it is appropriate for a tiny application intended to run without additional dependencies.

Rotating one player's interface

The first player has:

<div class="player rotate"></div>

while the second player only has:

<div class="player"></div>

The rotate class is not handled by JavaScript. It is presumably used by style.css to rotate the first player's controls.


This is particularly useful for a physical two-player device because the Kindle can be positioned between two players, allowing each player to view their own controls from their side.


The JavaScript remains completely unaware of the rotation. It only deals with the player's score.

The page reload button

At first i made this button so i could troubleshoot without restarting the kindle, but turns out that i can stick it so it refresh the life totals.


<button class="refresh" onClick="window.location.reload();"> ILC - LIFE COUNTER </button>

The initial HTML contains:

<h1 class="score">20</h1>

so reloading restores both players to 20 life.


This is another deliberately primitive solution. There is no local storage, database, cookies, application state, or reset logic.


For an old Kindle, this keeps the implementation extremely small.

Minimal JavaScript architecture

The entire application logic is essentially contained in one function:

function changeScore(button, amount) { const player = button.closest('.player'); const scoreElement = player.querySelector('.score'); scoreElement.textContent = parseInt(scoreElement.textContent) + amount; }

The function receives two pieces of information:


  • button — the button that was pressed.
  • amount — either 1 or -1.

The process is:

Button pressed

↓

Find its .player container

↓

Find that player's .score

↓

Read current score

↓

Convert text to integer

↓

Add or subtract 1

↓

Write new score to the page

Why this approach makes sense for Kindle

A modern implementation might use React, TypeScript, modules, bundlers, modern event APIs, local storage, or a more sophisticated state system.


None of those are necessary here.


The application only needs to perform three operations:

  • Detect a button press.
  • Identify the corresponding player.
  • Increase or decrease a number.

Using older browser-compatible techniques minimizes the amount of JavaScript that the Kindle needs to execute and avoids dependencies on modern browser APIs.


The project therefore intentionally prioritizes compatibility and simplicity over modern coding conventions.

HTML5-era considerations

Although the project uses an HTML5 doctype this should not be interpreted as meaning that the entire application depends on modern HTML5 APIs.


The page mostly uses HTML elements and behavior that were already familiar to older browsers. The HTML5 doctype is lightweight and allows the document to be interpreted using standards-oriented rendering where supported.


The important distinction is that HTML5 syntax and modern JavaScript APIs are not the same thing.


The project can use the HTML5 doctype while deliberately avoiding newer JavaScript features that would be problematic on an old Kindle.
